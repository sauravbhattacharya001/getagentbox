Module Architecture

Every module follows a consistent structure: a revealing module pattern (IIFE) assigned to a global variable. Modules self-initialize via DOMContentLoaded listeners or are bootstrapped from init.js. No imports, no bundler required at runtime.

var ModuleName = (function () {
  'use strict';

  // Private state
  var _el = null;

  // Public API
  function init(rootId) {
    _el = document.getElementById(rootId);
    if (!_el) return;
    // ... setup
  }

  return { init: init };
})();

Load Order

The build script (build.js) concatenates modules in dependency order into dist/bundle.js:

  1. Foundation: storage.js → dom-utils.js → globals.js
  2. Templates: _typing-indicator-template.js
  3. Modules: All 49 feature modules (order defined in build.js)
  4. Bootstrap: init.js (calls .init() on lazy modules)
  5. Top-level: benchmarks.js, command-reference.js, role-demo-picker.js, migration-guide.js, workflow-builder.js, capability-radar.js

Shared Utilities

Modules may depend on these shared globals (always loaded first):

  • DOMUtil.escapeHtml(str) — XSS-safe HTML encoding via a reused text node
  • AgentBoxStorage — Namespaced localStorage wrapper with JSON serialization
  • TypingIndicatorTemplate — Reusable three-dot typing animation HTML

Development Conventions

Adding a New Module

  1. Create src/modules/your-module.js using the IIFE revealing-module pattern
  2. Add the file path to the files array in build.js (before init.js)
  3. If the module needs explicit initialization, add a ModuleName.init('rootId') call in src/modules/init.js
  4. Add the corresponding HTML section in index.html with a unique ID matching the module's expected root
  5. Run npm run build to regenerate dist/bundle.js
  6. Add tests in __tests__/ following existing patterns (see Testing Guide)

Naming Rules

  • Global variable: PascalCase (e.g., ScenarioPlanner)
  • File name: kebab-case.js (e.g., scenario-planner.js)
  • DOM root ID: camelCase + Root or Section suffix
  • Private members: Underscore prefix (_el, _handleClick)

Security Requirements

  • All user-supplied strings must pass through DOMUtil.escapeHtml() before innerHTML insertion
  • No eval(), Function(), or inline event handlers
  • Respect the Content-Security-Policy: no inline scripts, no external script sources
  • Input length limits on any text field (see Playground's MAX_INPUT_LENGTH pattern)
  • DOM child limits to prevent memory exhaustion (see Playground's MAX_MESSAGES pattern)

Performance Patterns

  • Cache DOM references in module-level vars — resolve once in init(), reuse on every event
  • Use IntersectionObserver for scroll-triggered animations (never raw scroll listeners)
  • Lazy-init modules that aren't above the fold (register in init.js)
  • Use requestAnimationFrame for visual updates, never setInterval
  • Debounce resize/input handlers with setTimeout

Accessibility Checklist

  • All interactive elements must be keyboard-reachable (natural tab order or tabindex)
  • Use role, aria-label, aria-expanded attributes on custom widgets
  • Respect prefers-reduced-motion — disable or simplify animations when set
  • Color alone must never convey meaning — always pair with icons or text labels
  • Focus trapping required in modals and overlay components
