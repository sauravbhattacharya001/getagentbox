1. Security Overview

AgentBox is designed with a security-first architecture. Every component — from Telegram message ingestion to AI inference and memory storage — is built around the principle of least privilege and defense in depth.

Our security model is built on three pillars:

🏰

Defense in Depth

Multiple independent security layers ensure that no single point of failure can compromise user data.

🔑

Least Privilege

Every service, process, and API key has the minimum permissions required to function.

👁️

Transparency

Users can inspect, export, and delete their data at any time. No hidden data collection.

2. Architecture & Data Flow

The following diagram illustrates how messages flow through AgentBox's infrastructure:

┌──────────────┐ TLS 1.3 ┌──────────────────┐ mTLS ┌──────────────┐ │ Telegram │ ──────────────▶ │ API Gateway │ ───────────▶ │ Agent Core │ │ Client │ │ (Rate Limit, │ │ (Sandboxed) │ │ │ ◀────────────── │ Auth, WAF) │ ◀─────────── │ │ └──────────────┘ └──────────────────┘ └──────┬───────┘ │ ┌──────────────────────────────────┤ │ │ ┌──────▼───────┐ ┌─────────▼──────┐ │ Memory Store │ │ LLM Provider │ │ (Encrypted │ │ (No PII in │ │ at rest) │ │ prompts) │ └──────────────┘ └────────────────┘

Key architectural decisions:

  • No direct database exposure — all data access goes through the API gateway
  • Agent sandboxing — each agent runs in an isolated execution environment
  • PII stripping — personally identifiable information is redacted before reaching LLM providers
  • Ephemeral inference — LLM providers do not retain conversation data

3. Encryption & Key Management

In Transit

All external communication uses TLS 1.3. Internal service-to-service communication uses mutual TLS (mTLS) with automatically rotated certificates.

At Rest

User data is encrypted at rest using AES-256-GCM. Encryption keys are managed through a dedicated KMS (Key Management Service) with automatic rotation every 90 days.

Memory Encryption

Agent memory — the conversations and context your agent stores — is encrypted with a per-user key derived from your account credentials. Even AgentBox engineers cannot read your agent's memories without your key.

🔐 Key Hierarchy

Master Key (HSM) → Tenant Key (KMS) → User Key (derived) → Data Encryption Key (per-record). Keys are never stored alongside encrypted data.

5. Data Handling & Retention

What We Store

  • Conversations — encrypted message history for agent context
  • Agent Memory — structured knowledge your agent has learned (encrypted)
  • Usage Metrics — anonymized usage counts for billing and analytics
  • Account Data — Telegram user ID, display name, plan information

What We Don't Store

  • Raw audio or media files (processed transiently, then discarded)
  • Telegram messages outside your AgentBox conversation
  • Passwords (authentication is delegated to Telegram)
  • Payment card details (handled by our payment processor)

Retention & Deletion

You can delete all your data at any time via the /deletedata command. Data is permanently purged within 48 hours. Backups containing deleted data are purged within 30 days.

7. Incident Response

Our incident response plan follows industry best practices:

Response Timeline

  • < 15 minutes — Incident detected and response team alerted
  • < 1 hour — Initial assessment and containment
  • < 4 hours — Affected users notified (if data impacted)
  • < 24 hours — Root cause analysis published to status page
  • < 72 hours — Full post-mortem and remediation plan

We have never experienced a data breach. Our incident response plan is tested quarterly through tabletop exercises.
